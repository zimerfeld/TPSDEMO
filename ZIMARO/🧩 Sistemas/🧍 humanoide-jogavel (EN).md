# 🧍 Playable humanoid

> A third selectable character, with its OWN rig and animation vocabulary — and the seams that turned
> the `Player` class from "the robot" into a character chassis.
> Siblings: [[🧍 humanoide-jogavel (PT)|PT]] · [[🧍 humanoide-jogavel (ES)|ES]].
> See also [[🎮 player (EN)]], [[🎛️ controles-e-gestos (EN)]] and [[🧩 templates-de-level (EN)]].

## The blocker that shaped the design

**The player's speed doesn't come from code: it comes from the animation.** `apply_input` reads
`get_root_motion_position()` and divides by delta — the body travels exactly what the stride
travelled, which is why the feet never slide. There is no horizontal speed constant in `player.gd`.

Measured in both `.glb` files:

| model | `root` bone in `andar`/`correr` |
| --- | --- |
| `player.glb` | actually travels (`walking_gun` covers 2.18 m in 1.25 s) |
| `humanoide3.glb` | **zero** horizontal displacement — the animations are **in-place** |

Plugged into the player's engine, the humanoid would move its legs **standing still**. Retarget would
solve it (that's the FIGArtStudio path) but was ruled out of scope by the owner. The way out was
**speed-driven locomotion**: `_apply_horizontal_velocity` became **virtual** in the base, the humanoid
overrides it, and the animation cadence is scaled (`AnimationNodeTimeScale`) so the stride matches the
real speed — the same technique `red_robot` uses in manual movement.

> The swap does **not** fork the netcode: `_reconcile` is positional and agnostic to the speed source,
> and server and owning client both go through the SAME `apply_input`. Still one path, parameterised.

## The seams in the `Player` class

Four things tied the mechanics to the robot. All with defaults that keep `player`/`playera` identical:

| before | now | why it matters |
| --- | --- | --- |
| `player_model.get_node_or_null("Robot_Skeleton/Skeleton3D")` | `skeleton()`, searched by TYPE | `Robot_Skeleton` is the glTF root **inside** `player.glb`, not something authored. On another model it returned `null` **silently** → character with no limb damage and no procedural aim |
| `shoot_from` by literal path | search by the name `ShootFrom` | every model hangs the muzzle off a different bone |
| `model_key`/`head_shape`/… hardcoded in the method | `@export` (`limb_model_key`, …) | a subclass couldn't override them without rewriting the whole method |
| root-motion speed, directly | virtual `_apply_horizontal_velocity` | see above |

## The scene

`library3D/characters/humanoide_jogavel/humanoide_jogavel.tscn`, generated by
`scripts/build_humanoide_jogavel.gd` (re-running regenerates it).

**Its own folder, not inside `humanoide/`:** the replication whitelist matches
`basename == folder name`; outside it the `MultiplayerSpawner` **silently refuses** and the player is
invisible to the other peers.

**A flat copy, not an inherited scene:** the `playera` trick (instance `player.tscn` + script) doesn't
work — Godot won't let you repoint an inherited node's `PackedScene`, and the model is exactly what we
need to swap.

Two traps only the test caught, both silent:

1. **`PlayerModel` IS the `player.glb` instance**, not an empty node. Emptying it doesn't help: `pack`
   restores the children and the scene shipped with both models (145 robot bones instead of 16). Only
   replacing the node entirely with a same-named `Node3D` fixes it.
2. **Children added inside an instance** (the `GunBone`/`ShootFrom` on the skeleton) only survive
   `pack` if it's flagged with `set_editable_instance` — without it the character spawned with nowhere
   to shoot from.

## Animations

Scope of this delivery: **`ocioso`** idle, **`andar`** for any direction (W/S/A/D) and **`saltar`**.
The tree exposes the **same parameter names** `Player.animate()` already wrote
(`parameters/state/transition_request`, `walk`/`strafe` `blend_position`, `aim/add_amount`), so not a
line of that code changed.

Two `AnimationTree` traps on record: `walk`/`strafe` **must** be `BlendSpace2D` (the code writes
`Vector2`; a 1D rejects it every frame and the output freezes), and **collinear** points degenerate
the triangulation — hence the four cardinal points.

## Orientation, speed and cadence (2026-08-07, post-playtest)

**180° turn.** The humanoid's glTF was authored facing the OPPOSITE way from the player's: with the
same node transform, its mesh walked backwards. The fix is `rotation.y = PI` on the MODEL node (in the
generator), not in the logic — so movement direction, aim and muzzle keep speaking the same language
as the player and the red_robot.

> Measuring the NODE's angle doesn't expose this: humanoid and player transforms were identical. What
> differs is where the MESH points inside the `.glb`. It's a case only the eye catches — a playtest
> found it, not the automated tests.

**The animation looked rushed** because the cadence was `speed / 1.45` capped at **2.6×**: at 5.2 m/s
it hit the cap and played a WALK clip at nearly three times speed. Two changes fixed it:

1. The `walk` state became a progression **idle (0) → `andar` (0.45) → `correr` (1.0)**.
2. The cadence divides by the speed the clip REALLY represents, measured from its cycle length:
   `andar` 1.10 s ≈ **1.4 m/s**; `correr` 0.85 s ≈ **4.0 m/s**.

Measured afterwards: walking 1.70 m/s at **1.21×**; running 4.50 m/s at **1.12×**. The allowed range
is deliberately narrow (0.75–1.3) — needing 2× means the wrong clip is playing.

## Run, crouch and the aim shoulder

| key | effect |
| --- | --- |
| **SHIFT** (hold) | run: 4.5 m/s and the `correr` clip. Released, walks at 1.7 m/s with `andar` |
| **CTRL** (hold) | crouch: `ajoelhar_dir` or `ajoelhar_esq` **following the aim side**; releasing aborts the gesture |
| **C** | flips the aim shoulder and REMEMBERS it (`Settings → reticle_side`) |

All three are remappable actions in the Controls tab. **`running` and `crouching` are REPLICATED**:
without that the server would simulate walking while the client runs, and reconciliation would start
correcting a divergence that is purely input — the same mechanism that produces "flickering".

The aim side is applied **after** the camera animation, mirroring the `SpringArm3D` X: the aim clip
stays single, it just switches shoulders.

## Numbers to eyeball

`MAX_SPEED = 5.2 m/s` and the camera height `1.72 m` are **estimates**. One constant each.

## Registering in the selector

`PlayerSelection.VARIANTS` and `chooseplayer.CHARACTERS` must stay in the **same order** — what
travels over the network is the **index**. Always append at the end; inserting in the middle makes
players spawn with the wrong body on every peer, and the clamp hides it.

The screen's preview is no longer hardcoded to `player.glb`: each character declares `model_glb` and
`idle_anim` (the robot rests in `Idlecombatrest`; the humanoid, in `ocioso`).

**Bug fixed along the way:** the name Label entered the tree with the text `"PLAYER"`, which `Locale`
freezes as its source — switching languages reverted the name to "PLAYER". Fixed by putting the node
in the manual-translation group (a proper name is data, not dictionary material).
